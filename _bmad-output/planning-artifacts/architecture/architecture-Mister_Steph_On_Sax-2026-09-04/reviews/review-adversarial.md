# Adversarial Divergence Review — Mister Steph On Sax Architecture Spine

## Verdict

The spine is solid on the big Client/Server and provider-lock decisions but has several real gaps where two units can each satisfy every AD to the letter and still ship incompatible code — most notably a literal file-naming contradiction inside the document itself, an unpinned "type de prestation" value list duplicated across two ADs, and an incomplete Server Action failure contract.

## Findings

- **critical** Consistency Conventions says "Composants en PascalCase (`ContactForm.tsx`)", but the Structural Seed lists every component file in lowercase/kebab-case (`hero.tsx`, `listen-teaser.tsx`, `formules.tsx`, `contact-form/contact-form.tsx`). A unit that follows the Conventions table literally builds `components/Hero.tsx`/`components/ContactForm.tsx`; a unit that follows the Structural Seed literally builds `components/hero.tsx`/`components/contact-form/contact-form.tsx`. Both comply with a section of the spine, yet imports collide/mismatch (case-sensitive on Vercel's Linux build even if fine locally on a case-insensitive filesystem). (location: Consistency Conventions × Structural Seed). *Fix:* delete the PascalCase example from Consistency Conventions (or rewrite the Structural Seed in PascalCase) so exactly one naming rule survives, and restate it as part of AD-1 or a dedicated naming AD since it's structural, not a soft convention.

- **critical** The list of "type de prestation" values is required to be single-sourced twice, in two different files, by two different ADs, with no rule tying them together. AD-5 says the `<select>` options live in `lib/content.ts` (and are reused by email templates); AD-3 says validation lives in a single Zod schema in `lib/validation.ts`. A unit building the form/content (AD-5) and a unit building the Zod schema (AD-3) can each honor their own AD perfectly while defining the allowed-values list independently — e.g. content.ts ships 5 offering types, validation.ts's z.enum still lists an older set of 4, or the slugs are spelled differently (`"mariage"` vs `"wedding"`/`"Mariage"`). Result: a value selectable in the UI gets rejected server-side as an invalid enum, or vice versa. (location: AD-3 × AD-5). *Fix:* add a rule (or amend AD-3/AD-5) mandating that `lib/validation.ts`'s enum for "type de prestation" is derived from the same array exported by `lib/content.ts` (e.g. `z.enum(prestationTypes.map(p => p.value))`), not redeclared.

- **high** AD-3 pins the Server Action's return contract to exactly `{ ok: true } | { ok: false, fieldErrors: Record<string,string> }`, but that shape has no slot for a failure that isn't a validation error — i.e. Zod passes, but AD-4's `resend.batch.send(...)` call throws or returns an error. Two units can each satisfy AD-3's literal shape while handling this case incompatibly: one stuffs a synthetic key into `fieldErrors` (e.g. `fieldErrors: { _form: "Erreur d'envoi, réessayez" }`), the other extends the discriminated union with a third case (e.g. `{ ok: false, formError: string }` or an optional `message` field). The Client Component built against one shape breaks against an `actions.ts` built to the other. (location: AD-3 × AD-4). *Fix:* extend AD-3's contract explicitly, e.g. `{ ok: true } | { ok: false, fieldErrors: Record<string,string> } | { ok: false, formError: string }`, and state which case a Resend failure maps to.

- **high** AD-3 requires the Client Component to consume the Server Action's return value for field-level error display, which in React/Next.js typically means wiring the action through `useActionState` (signature `(prevState, formData) => result`). AD-2's diagram, however, shows the action wired directly as `<form action={...}>` (bare `(formData) => result` signature, no returned state hook-up implied). A unit writing `lib/actions.ts` could pick either signature; a unit writing `contact-form.tsx` could independently choose `useActionState` or a manual `startTransition` + local `useState` around a plain action — two mutually incompatible wiring conventions, both consistent with "the Server Action returns `{ok,...}` and is passed to `<form action>`" as literally written. (location: AD-2 × AD-3). *Fix:* pin the exact Server Action signature (`useActionState`-compatible `(prevState, formData)`, or state explicitly that it is not) as part of AD-2 or AD-3.

- **medium** AD-5's boundary between "texte éditorial métier" (must live in `lib/content.ts`) and "texte d'interface générique" (implicitly free to hardcode) is not objectively testable, and AD-5's explicit `Binds` list only names "cartes Formules, options du menu déroulant, copy teaser Écoute" — it does not mention contact-form field labels (`Nom`, `Email`, `Message`, submit-button text) or the boilerplate greeting/signature copy inside `emails/notification-email.tsx` / `confirmation-email.tsx`. A unit building `ContactForm` can legitimately hardcode field labels as "generic UI text"; a unit building the email templates can legitimately hardcode the email's opening/closing lines as template-specific text — while another unit, reading AD-5's stated intent ("tout texte éditorial vit dans lib/content.ts"), centralizes the same strings. Either choice is defensible under the letter of AD-5, but the two units end up with an inconsistent codebase (some brand copy centralized, some not) and, per AD-5's own stated failure mode, no single place to fix wording later. (location: AD-5). *Fix:* extend AD-5's `Binds` list to explicitly cover contact-form field labels/CTA text and email boilerplate, or state a concrete test (e.g. "any string a non-technical Stephane might want to edit goes in content.ts; only ARIA/technical strings stay inline").

- **medium** No canonical shape/interface is pinned for `lib/content.ts`'s exports. AD-5 mandates a single file and that it's "typed," but not the field names or structure. The Formules-component author and the email-template author are both required consumers (per AD-5's own text: "importé par les composants ET par les templates d'email qui en ont besoin"), yet nothing stops one from defining `{ titre, description, prix }` and the other from expecting/adding a second, differently-shaped export (`{ title, price, features[] }`) for the same concept when they build in parallel, since AD-5 never names the exported symbols or their fields. (location: AD-5). *Fix:* add a minimal TypeScript interface (or literal export names) for the Formules and "type de prestation" content shapes directly into the spine (or into `lib/content.ts` before either consumer is built) so both units import the same symbol instead of each defining their own.

- **medium** The "from" sender identity (display name + address used in `resend.batch.send`) has no designated home. AD-7's `Binds` list names exactly two env vars (`RESEND_API_KEY`, `CONTACT_TO_EMAIL`); AD-5's content centralization only covers "texte éditorial métier," which a unit could argue excludes a technical sender address. One unit can hardcode the from-string as a literal inside `lib/resend.ts` (e.g. `"Mister Steph On Sax <contact@domaine.fr>"`); another can introduce an unlisted env var (`EMAIL_FROM`, `RESEND_FROM_EMAIL`, ...) for the same value, assuming AD-7's environment-variable convention should extend to it. Neither violates any AD as written, but they produce divergent configuration surfaces. (location: AD-4 × AD-7). *Fix:* explicitly name the from-address's home (env var name, or a named constant in `lib/resend.ts`) in AD-4 or AD-7.

- **medium** No AD addresses spam/bot protection for the public contact form, even though every submission triggers two paid Resend sends (AD-4). Nothing forbids one unit from bolting on a Turnstile/reCAPTCHA check implemented as a dedicated `app/api/verify-captcha/route.ts` (which would break AD-2's "no dedicated API route for this flow" only if a reviewer judges captcha verification to be "part of this flow" — a judgment call the AD doesn't settle), while another unit does an inline honeypot-field check purely inside `lib/actions.ts`. If a client-verification approach is chosen, it would also introduce a new `NEXT_PUBLIC_*` env var and a server-side secret (e.g. `TURNSTILE_SECRET_KEY`) that AD-7's two-variable `Binds` list doesn't anticipate, so naming/placement is left to whichever unit gets there first. (location: AD-2 × AD-7 / Deferred-adjacent, not actually listed under Deferred). *Fix:* either add an explicit AD stating the chosen anti-spam mechanism (or "none, revisit later" as an explicit Deferred entry with a Prevents clause blocking ad hoc additions), and if any secret is needed, name its env var now.

- **low** AD-6 pulls only `colors`/`typography`/`rounded` 1:1 from `DESIGN.md`'s frontmatter into the `@theme` block. If `DESIGN.md` defines other token categories (spacing scale, shadows, breakpoints), AD-6 is silent on whether those must also be tokenized in `@theme` or may be used as arbitrary Tailwind values — two components could diverge on ad hoc `p-[23px]`-style magic numbers versus theme-token spacing without either violating AD-6's literal text. (location: AD-6). *Fix:* either state AD-6 covers "all token categories present in DESIGN.md's frontmatter, whatever they are," or enumerate the exhaustive list actually present in DESIGN.md.

- **low** The Stack table pins exact versions for Next.js (16.3.4) and Zod (4.5.4) but leaves Resend and `@react-email/components` at "dernière version" with no pin. Two units built at different times (or by different coding agents fetching "latest" independently) can install different major versions of either SDK; both React Email and Resend have shipped breaking API changes across majors (component/`render()` API, `batch.send` payload shape). This isn't forbidden by any AD, and would only surface as a build/runtime break when the two units' code is integrated. (location: Stack table). *Fix:* pin exact versions for `resend` and `@react-email/components` the same way Next.js/Zod are pinned.

- **low** Deferred items differ from ADs in that they carry no `Prevents` clause, so nothing actually stops a unit from acting anyway. This mostly doesn't matter (the audio player and i18n items are effectively already blocked by AD-1's "no interactivity" rule and by AD-5's "une seule langue" rule respectively, and Cloudinary is moot since the launch UX direction has no photos at all), but Analytics is genuinely unguarded: one unit could proactively add `@vercel/analytics`/`SpeedInsights` to `app/layout.tsx` (a common default in Next.js/Vercel scaffolds) while another omits it entirely, per the Deferred note's stated intent ("aucun outil de suivi... n'a été demandé"). This also surfaces an unaddressed RGPD/cookie-consent question for a French-facing site that no AD or Deferred item currently owns. (location: Deferred — Analytics/observabilité). *Fix:* give the Analytics Deferred item an explicit Prevents clause ("no analytics/tracking script is added until this is revisited"), matching how the ADs are enforced.

- **low** AD-1's parenthetical "(et sa région live de feedback)" leaves the location of the live/`aria-live` feedback sub-region ambiguous: it could stay inline inside `contact-form/contact-form.tsx`, or be factored into a second client component. If factored out, nothing says it must stay under `components/contact-form/` (matching the Structural Seed) rather than becoming a top-level, more "global-feeling" component (e.g. `components/toast.tsx`) — which would also sit in tension with the Consistency Conventions row stating "le seul état vit localement dans ContactForm." (location: AD-1). *Fix:* state explicitly that any sub-component for the live feedback region must live under `components/contact-form/` and receive its state as props from `ContactForm`, never hold independent state.
