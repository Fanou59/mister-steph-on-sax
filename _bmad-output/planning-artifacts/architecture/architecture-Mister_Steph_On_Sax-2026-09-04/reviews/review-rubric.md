# Rubric Walker Review — Mister Steph On Sax Architecture Spine

## Verdict

Solid, appropriately terse spine that correctly defers to EXPERIENCE.md/DESIGN.md and keeps the Server/Client boundary consistent throughout, but the Server Action's result contract (AD-3) doesn't actually cover the technical-failure state EXPERIENCE.md requires, and two operational-envelope risks (Resend batch atomicity, live emails from Preview deployments) are undecided and unflagged.

## Findings

- **high** AD-3's Server Action contract `{ ok: true } | { ok: false, fieldErrors: Record<string,string> }` has no shape for the "échec technique (email non envoyé)" state that `EXPERIENCE.md § State Patterns` explicitly requires (a `role="alert"` generic failure message, distinct from the per-field `aria-invalid`/`aria-describedby` validation errors on blur/submit). As written, the Client Component and `lib/actions.ts` have no shared contract for a non-field error, so two implementers will diverge on how to represent it (e.g. stuffing a fake key into `fieldErrors`, vs. throwing and catching client-side, vs. inventing a third field) — exactly the kind of divergence this altitude exists to prevent, and it sits on the one truly interactive part of the page. (location: AD-3). *Fix:* extend the return type, e.g. `{ ok: true } | { ok: false, kind: 'validation', fieldErrors } | { ok: false, kind: 'technical' }`, and bind it to both the Client Component's error UI and the Server Action.

- **medium** AD-4 mandates a single `resend.batch.send([...])` call per submission for both the Stephane-notification and visitor-confirmation emails, but Resend's batch endpoint is atomic — if either email fails validation (e.g. a malformed-but-Zod-passed edge case, sandbox/testing restrictions, or a rejected recipient), the *entire batch* fails, including the notification email whose entire purpose is to guarantee Stephane hears about every lead even if something else goes wrong. AD-4 doesn't acknowledge or rule on this failure mode, and AD-3's contract (see above finding) has nowhere to represent "notification sent, confirmation failed" vs "both failed" differently even if it wanted to. (location: AD-4). *Fix:* either accept the atomic-failure tradeoff explicitly (state it as a rule so it isn't "discovered" later), or split into two calls / prioritize the notification send.

- **medium** AD-7 places `RESEND_API_KEY` and `CONTACT_TO_EMAIL` in Vercel env vars for "Production + Preview" (per `.memlog.md`'s adopted deployment decision, echoed in the Stack table's "Vercel (Production + Previews automatiques)"), but nothing decides whether automatic PR/branch Preview deployments should actually fire live emails through the same Resend key to Stephane's real inbox. This is a real operational-envelope gap for a form whose whole job is triggering outbound email — a contributor testing the form on a preview URL will silently spam the production notification address. (location: AD-7 / Stack § Déploiement). *Fix:* either scope `CONTACT_TO_EMAIL`/send behavior differently per environment (e.g. a test recipient or a `NODE_ENV`/`VERCEL_ENV` gate) or explicitly rule that Preview intentionally reuses production email delivery.

- **medium** No decision, and no explicit Deferred entry, addresses spam/abuse protection on the public contact form (honeypot, rate limiting, CAPTCHA) — not raised anywhere in `.memlog.md` either. This is a silent dimension for a form that causes real outbound email sends (cost + inbox spam risk for Stephane) once the site is public; absent an explicit call, future contributors will diverge on whether/how to add protection, or ship without any. (location: whole document / Deferred). *Fix:* add a one-line Deferred bullet (e.g. "no anti-spam measures at launch; add honeypot/rate-limit if abuse appears") so it's a tracked decision rather than an unstated gap. Related and lower-stakes: double-submit protection is scoped client-side only (`aria-disabled`/`aria-busy` per EXPERIENCE.md) with no server-side idempotency, so a bypassed client guard can still produce duplicate batch sends — worth folding into the same note.

- **low** The Stack table pins exact versions for Next.js (`16.3.4`) and Zod (`4.5.4`) but leaves Resend and React Email as "dernière version SDK"/"dernière version stable" — an inconsistent pinning strategy. Verified live: Resend's batch endpoint recently gained idempotency-key support, so an unpinned install a few weeks apart between two contributors could see real API-surface differences. (location: Stack table). *Fix:* pin exact versions for Resend/React Email too, consistent with the rest of the stack, or explicitly note versions are to be pinned in `package.json` at implementation start.

Verified and found accurate (no finding, noted for completeness): Next.js 16.3.4, Zod 4.5.4, Tailwind v4 CSS-first `@theme`, and React 19.x bundled with Next.js 16 (confirmed 19.2) all check out against current docs/releases as of this review — the named-tech table is asserted correctly, not fabricated.
