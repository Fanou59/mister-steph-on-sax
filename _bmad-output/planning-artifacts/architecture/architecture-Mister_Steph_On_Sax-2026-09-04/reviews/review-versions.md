# Version Verification Review — Mister Steph On Sax Architecture Spine

## Verdict

Most of the stack checks out — Next.js 16.3.4, Zod 4.5.4, Tailwind v4's `@theme` CSS-first config, Resend's `batch.send()` API, and Server Actions as the idiomatic App Router form pattern were all confirmed accurate against live sources as of 2026-09-04. However, the spine names `@react-email/components`, which has been deprecated for nearly five months (since React Email 6.0, April 16, 2026) in favor of the unified `react-email` package — this reads as an unverified, training-data-era assumption, not a checked claim. The `TypeScript 5.x` pin is also stale relative to the ecosystem (TS is on 6.0/7.0 as of March/mid-2026) though not technically broken.

## Findings

- **high** Stack table lists `React Email (@react-email/components)` as the library, and the Structural Seed / AD-4 build the email templates against that same package. `@react-email/components` has been deprecated since React Email 6.0.0 (April 16, 2026, ~5 months before this spine's creation date) — the changelog states "`@react-email/components` and individual component packages are no longer needed," replaced by a single unified `react-email` package (latest confirmed: 6.9.3). This is a superseded/deprecated dependency asserted without a version check; a fresh project started today should import from `react-email`, not `@react-email/components`. (location: § Stack row "React Email (`@react-email/components`)"; also Structural Seed `emails/*.tsx`, AD-4). *Fix:* Update the Stack table and Structural Seed to specify the `react-email` package (pin or "latest stable react-email package, not @react-email/components"), and note the migration explicitly so a builder doesn't reach for the deprecated package out of habit/training data.

- **medium** TypeScript is pinned to "5.x" with no version researched or justified. As of 2026-09-04, TypeScript's own release line has moved past 5.x: TS 5.9 (Aug 2025) was the last 5.x release, TS 6.0 shipped March 17, 2026, and TS 7.0 (Go-ported, ~10x faster type-checking, and explicitly usable by `next build` per the Next.js 16.3 blog) is now current (latest patch 7.0.2). Next.js 16's own upgrade guide only requires "TypeScript 5+ (minimum 5.1.0)," so 5.x will not break the build, but the spine presents "5.x" as if it were still the current/default choice rather than a deliberately-retained older major — nothing in the AD text acknowledges 6.x/7.x exist or explains why 5.x was kept. This pattern (unqualified "5.x") is consistent with an assertion from training data rather than a live check. (location: § Stack row "TypeScript | 5.x"). *Fix:* Either bump the pin to TypeScript 6.x/7.x and confirm compatibility with the rest of the toolchain (ESLint flat config, ts-node if used, etc.), or explicitly state the rationale for staying on 5.x (e.g., ecosystem/tooling lag) so it reads as a decision, not an oversight.

- **low** The Stack table gives exact, verifiable version numbers for Next.js (16.3.4) and Zod (4.5.4) that match the actual latest published releases as of today almost to the day — strong evidence those two were genuinely checked against npm/release notes. By contrast, Resend and React Email are both left as "dernière version" (latest, unspecified) with no number pinned at all. This inconsistency in rigor is itself a signal: the two unpinned entries are exactly the ones where a real check would have surfaced a problem (see the `@react-email/components` deprecation above; Resend's own `resend` npm package is fine, currently 6.26.0 and actively released, batch.send confirmed working as documented). (location: § Stack rows "Resend" and "React Email"). *Fix:* Pin both to the version actually verified at spine-writing time (or at minimum name the correct current package for React Email), rather than leaving them as an unverified "latest."

- **low** AD-3's return contract (`{ ok: true } | { ok: false, fieldErrors }`) is compatible with, but doesn't reference, `useActionState` — the pattern current 2026 guidance calls out as the recommended way to wire pending/error state for Server-Action-backed forms in the App Router. Not a version error, just an omission that a builder implementing the Client island might miss. (location: AD-3, AD-2). *Fix:* Optionally note in AD-3 or the Structural Seed that `ContactForm` should consume the action via `useActionState` for pending/error UI, to remove any ambiguity for the implementer.

- **informational (no fix needed)** Confirmed accurate and current, no action needed: Next.js 16.3.4 exact match to the latest published release (nextjs.org/docs, lastUpdated 2026-08-25); React/React DOM 19.x correctly described as bundled with Next.js 16 (React 19.2 canary line, latest patch 19.2.8, no 19.3/React 20 announced); Tailwind CSS v4's CSS-first `@theme` directive is accurately described (custom properties in `@theme` generate both CSS variables and Tailwind utility classes, no `tailwind.config.js` needed); Resend's `resend.batch.send([...])` API is real, current, and matches the spine's usage shape (up to 100 emails per call, one call per submission for notification + confirmation); Server Actions (not a dedicated API route) remain the current idiomatic Next.js App Router pattern for form mutations in 2026, with Route Handlers reserved for public/webhook/third-party-callable endpoints — matching AD-2's rule exactly; Vercel remains the dominant, fitting deployment target for this stack, no better-fit alternative surfaced for a small Next.js landing page + contact form + transactional email use case.
