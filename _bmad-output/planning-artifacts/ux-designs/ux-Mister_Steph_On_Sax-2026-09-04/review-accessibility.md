# Accessibility Review — Mister Steph On Sax

## Overall verdict

Core reading-text pairings are strong: ink-on-surface (~14:1), on-navy-on-navy (~14:1), on-navy-soft-on-navy (~9.3:1, still ~7.1:1 even after the hero's 85% opacity reduction), on-gold-on-gold (~5.8:1), on-sage-on-sage (~5.6:1), and ink-soft-on-surface-card (~7.5:1) all pass WCAG AA comfortably. However, one genuine WCAG contrast failure exists in the eyebrow-label color rule, and EXPERIENCE.md's form-error/submission-state behavior leaves several standard a11y mechanics (focus loss on disable, dynamic announcement of success/failure, blur-vs-submit focus handling) unresolved — these are real gaps a Next.js implementer would need to invent, and could easily invent unsafely. Non-text (border) contrast is also below AA's 1.4.11 minimum for form-field/card boundaries.

## Findings

- **critical** Eyebrow text rule is contrast-unsafe on light backgrounds. DESIGN.md's Typography section says eyebrow labels are "toujours en `{colors.gold}` ou `{colors.sage}` selon le fond," but computed against `{colors.surface}` (#F8F6F0), gold (#C59B27) yields only ≈2.4:1 and sage (#84A59D) only ≈2.48:1 — both fail WCAG AA's 4.5:1 for this non-large (12px/0.75rem bold, below the 14pt-bold "large text" threshold) text. Both of the document's own candidate eyebrow colors fail on the surface background used by the Présentation & Formules and Contact/Devis sections. (location: DESIGN.md § Colors, § Typography) *Fix:* explicitly map background → eyebrow color per section, and for light/surface backgrounds specify a dark eyebrow color (e.g. `ink` or a darkened gold/olive) verified ≥4.5:1; reserve gold/sage eyebrow text for the navy background only, where gold measures ≈5.8:1.

- **high** No error/danger color token exists anywhere in DESIGN.md's `colors` or `components` frontmatter, despite EXPERIENCE.md requiring per-field inline validation messages ("Message précis sous le champ concerné"). A downstream implementer has no vetted, contrast-checked color to use for error text/icon/border. (location: DESIGN.md § frontmatter colors, § Components; EXPERIENCE.md § State Patterns "Formulaire — erreur de validation") *Fix:* add an explicit error token (e.g. `error` / `on-error`) to DESIGN.md with a contrast value checked against `surface` and `surface-card`.

- **high** The "bouton d'envoi désactivé pendant l'envoi" spec doesn't address the standard focus-loss anti-pattern: applying the native `disabled` attribute to the button the user just activated removes it from the tab order and typically drops focus to `<body>`, disorienting keyboard/screen-reader users mid-submission. (location: EXPERIENCE.md § Component Patterns "Bouton d'envoi", § State Patterns "envoi en cours") *Fix:* specify `aria-disabled="true"` + `aria-busy="true"` (keeping the button focusable and preventing re-activation via script) instead of the native `disabled` attribute, or require explicit refocus/announcement after the state change.

- **high** Success and failure submission outcomes have no specified announcement mechanism for assistive tech. "Le formulaire est remplacé par un message de confirmation" and the technical-failure message are described only visually; without an `aria-live`/`role="status"`/`role="alert"` region or an explicit focus move to the new message, screen-reader users who submitted via keyboard have no way to learn the outcome. (location: EXPERIENCE.md § State Patterns "Formulaire — succès", "Formulaire — échec technique", § Key Flows) *Fix:* require the confirmation message to be a `role="status"` (polite) region and the failure message a `role="alert"` (assertive) region, or specify a focus move to the new content on both outcomes.

- **medium** Non-text contrast of `{colors.border}` (#E4E1D8) against both `{colors.surface}` (≈1.2:1) and `{colors.surface-card}` (≈1.3:1) falls far short of WCAG 1.4.11's 3:1 minimum for UI-component boundaries. This is the sole boundary cue for `form-field` and `formule-card` per DESIGN.md's Components table, and card-background-vs-page-background itself differs by only ≈1.08:1 — so low-vision users may not perceive where an input field or card begins/ends. (location: DESIGN.md § Colors "border", § Components "form-field", "formule-card") *Fix:* darken the border token for form-field/card usage, or add a secondary visual cue (shadow, stronger border) meeting ≥3:1 against the adjacent surface.

- **medium** Unreconciled conflict between "Validation au blur" (Component Patterns, applies per-field to Nom/Prénom/Date/Lieu) and "focus déplacé au premier champ en erreur" (State Patterns, reads as submit-time behavior — matches the Key Flows, which only show errors surfacing at submit). It's not specified whether a blur-triggered error also yanks focus back to the field the user just left (unusual/disruptive), or whether blur errors instead rely solely on `aria-describedby`/`aria-invalid` without any focus move — and if the latter, there's no live-region requirement to ensure the newly-shown blur error is announced at all. (location: EXPERIENCE.md § Component Patterns "Champ de formulaire", § State Patterns "erreur de validation") *Fix:* clarify that blur-time errors surface via `aria-describedby`/`aria-invalid` in place, without a focus jump, and that focus-jump-to-first-error is specifically a submit-time behavior.

- **medium** No focus-indicator color or contrast value is specified — only "contour perceptible... jamais supprimé sans remplacement." Given the low-contrast border/background tokens already flagged, a default browser outline or a reused low-contrast token risks failing the ≥3:1 requirement (WCAG 1.4.11) for focus indicators on form fields and cards on light backgrounds. (location: EXPERIENCE.md § Accessibility Floor) *Fix:* specify an explicit focus-ring color/width in DESIGN.md, verified ≥3:1 against both `surface` and `surface-card`.

- **low** The Hero badge/insigne and the Écoute section's static sound-wave visual are not explicitly marked as decorative for assistive tech. Both are purely ornamental (the badge's meaning duplicates the adjacent "Mister Steph On Sax" H1/wordmark; the waveform is static and non-functional), but EXPERIENCE.md never states they should get empty `alt=""` / `aria-hidden="true"`, risking redundant or meaningless screen-reader announcements. (location: EXPERIENCE.md § Component Patterns "Insigne / badge", "Bloc Écoute (teaser)") *Fix:* add a line stating both graphics are decorative-only (`alt=""` / `aria-hidden="true"`).

- **low** EXPERIENCE.md correctly specifies a native `<select>` for "Type de prestation" (inherently keyboard/AT-operable) but doesn't warn against a future re-implementation as a styled custom listbox/combobox, which would need its own accessible-pattern rebuild (roving tabindex, `aria-activedescendant`, etc.). (location: EXPERIENCE.md § Component Patterns "Champ de formulaire") *Fix:* add a note restricting the select to CSS-only styling of the native element unless a full ARIA combobox pattern is implemented.

- **low** No document-language requirement (`<html lang="fr">`) is stated anywhere, which affects screen-reader pronunciation of the entirely French content; also no explicit skip-link/landmark guidance is given for the single long-scroll page beyond the Hero CTA anchor (which likely doubles as a de-facto "skip to form" for keyboard users, but this isn't stated). (location: EXPERIENCE.md § Foundation, § Accessibility Floor) *Fix:* note `<html lang="fr">` as a build requirement, and confirm/state that the Hero CTA anchor serves as the skip-to-form mechanism.
